# JoyChord — Web Synth

JoyChord is an installable PWA HiChord-inspired chord synthesizer. Web Audio API, no build step, no dependencies, no bundler. `index.html` holds markup only; `style.css` and `src/*.js` (loaded as ES modules via plain `<script type="module" src="src/index.js">`, no bundling) hold styling and logic respectively. `manifest.webmanifest` + `sw.js` + `icons/` make it installable/offline-capable — see PWA below, including a real gotcha around keeping `sw.js`'s precache list in sync with the actual `src/*.js` files.

**Live:** https://millllllz.github.io/joy-chord/
**Repo:** https://github.com/millllllz/joy-chord (public, `master` branch, deploys via GitHub Pages on push)
**Current build:** v48 (bottom-left corner of the app; bump on every deploy, see Conventions)

## Orientation for a new agent

- There is no build step and no test runner. "Testing" means opening `index.html` (locally or via the live URL) in a browser and interacting with it — see Conventions below for the verification bar expected before calling a UI change done.
- Logic lives in `src/*.js` ES modules (one concern per file — `audio.js`, `effects.js`, `degree-joystick.js`, `modifier-joystick.js`, `chords.js`, `settings.js`, `wedge-geometry.js`, `debug.js`, `fullscreen.js`, wired together by `index.js`), styling in `style.css`, and `index.html` holds only markup (static SVG defs; joystick wedges/labels/dots are built at runtime by the JS). When you add or rename a `src/*.js` file, update `sw.js`'s `ASSETS` precache list to match — it's a hand-maintained mirror of that directory, not auto-derived.
- `master` is production and deploys on push (GitHub Pages). There is standing authorization to push directly to `master` without asking first — see Conventions.
- `todo.md` exists in the working directory but is gitignored — it's the user's personal scratch list, not project documentation. Open items from it are folded into "Known open items" below when they're still relevant; don't treat `todo.md` itself as authoritative if it and this README disagree.

## Naming

- **Degree joystick** — the left stick, 7 wedges, one per diatonic **chord degree** (I, ii, iii, IV, V, vi, vii°).
- **Modifier joystick** — the right stick, 8 wedges, changes the quality/extension of whichever degree is held.
- **Stick dot** — the small knob on each joystick that tracks the raw pointer/touch position continuously, layered on top of the discrete wedge zones.

Not "Nashville numbers" — that term belongs to a different, unrelated chart notation.

## Architecture

Two side-by-side SVG joysticks, controller-style:

- **Degree joystick** (left, 7 wedges): diatonic scale degrees I–vii° in the current key, each with its own natural triad quality (major/minor/diminished). Hover/touch/keyboard (`a s d f` odd, `w e r` even, or `1`-`7`) to play. Wedge/center labels are case-sensitive on purpose (I vs ii vs vii°) — this is the one place case carries meaning, so `.degree-label`/`.degree-center-label` never get `text-transform`.
- **Modifier joystick** (right, 8 wedges): HiChord-style chord modifications (maj/min toggle, dom7, 7th, add9, sus4, add6/sus2, darken, aug) applied relative to whichever degree's natural quality is held — not always a major base, *except* dom7 (`up-right`) and aug (`up-left`): both force a major 3rd regardless of the held triad's own quality, since that's literally what makes a chord "dominant" or "augmented" — a minor degree's Dom7 is a true dominant 7th (`D7`, major 3rd + flat 7), not a minor 7th (`Dm7`), and its Aug is a true augmented triad (`Daug`, major 3rd + raised 5th), not a "minor #5". Every other wedge (7th, add9, sus4/sus2, add6, darken) does layer onto the held triad's own quality. Static wedge labels are uppercase (`.joy-label`, by explicit user preference — an intermediate case-sensitive version was tried and reverted); the center label (`.joy-center-label`) is the one exception, since it holds the dynamic chord-name readout (see below), not fixed text, and a chord name needs mixed case to read correctly — kept case-sensitive there by a later, separate explicit request. The 4 quality-dependent wedges (`MAJ/MIN`, `MAJ7/MIN7`, `6TH/SUS2`, `DIM/MIN`) are always split into two stacked `<tspan>` lines via `renderJoyLabel()` in `src/modifier-joystick.js`, since SVG `<text>` doesn't wrap and these are too wide for one line at wedge scale; once a chord resolves, the option that doesn't apply is dimmed (`.joy-label tspan.dimmed`, opacity 0.35) rather than removed, so the wedge always shows both options and doesn't jump between one-line and two-line layouts as chords change.
- **"left" (darken) direction**: deviates from the manual on purpose — major/minor both go to diminished, and diminished (vii°) steps to minor (the only way to reach a plain minor triad on that button, since nothing else produces one there).

A `<select>` dropdown transposes all 7 degrees together (global key root, semitone offset from C). Its options list starting at A (conventional listing order) rather than C, but each option's `value` still carries its real semitone-from-C offset — `KEY_NAMES` itself stays C-first (index 0 = C = 0 semitones), since that indexing is also every existing `currentKeyRoot` number's meaning; only the *display* order in `settings.js`'s `init()` is rotated. The dropdown still defaults to C regardless of where C lands in that rotated list. A second `<select>` picks the oscillator waveform (sine/square/sawtooth/triangle), applied to every voice via `osc.type` — `setWaveType()` in `src/audio.js` also walks `audio.voices` so a change is audible on a chord that's already held, not just the next note. `audio.currentWaveType` is the single source of truth here; `src/settings.js` only wires the dropdown to it (it previously kept its own `settings.currentWaveType`, which nothing read — the dropdown silently did nothing).

**Layout**: `.joysticks` is a CSS grid in both orientations. `.controls` — a real `<fieldset>`, the single bordered "set of all controls" panel — is the grid child; `.fx-toggles` (the effect/behavior toggle buttons) and `.sound-controls` (the key/wave `<select>`s) are plain `<div>`s inside it, each with its own small uppercase label (`.controls-group-label`), not their own borders — two sub-groups sharing one box, not two separate boxes. Portrait stacks the two joysticks in rows 1/3 with `.controls` in row 2 between them, both sub-groups laid out as horizontal rows; landscape puts the joysticks in columns 1 and 3 with `.controls` in column 2, and both sub-groups switch to `flex-direction: column` so their contents stack vertically instead of squeezing a wide row into the narrow middle column. Nothing is absolutely positioned over the grid — an earlier version floated `.fx-toggles` on top with `z-index: 1000` and it swallowed taps meant for the dropdowns in landscape.

**Portrait joystick sizing is space-derived, not a fixed fraction**: each `.joystick` used to be `width: min(45dvh, 96vw)` — a fixed 45% of viewport height regardless of how tall `.controls` actually was. That silently stopped fitting once `.controls` grew past whatever 45dvh×2 had left room for (it's grown several times over — the FX/Sound labels, the border, seven buttons wrapping to two rows on narrow phones) and clipped the bottom joystick off-screen with no way to scroll to it (`body` is `overflow: hidden`). Fixed by making `.joysticks`' portrait `grid-template-rows` `1fr auto 1fr` on a grid given a real `height: 100%`, so the two joystick rows always get an equal share of *whatever's actually left* after the controls row takes what it needs — `.joystick` itself is `height: 100%; width: auto; aspect-ratio: 1;` (deriving width from its row's real height) with `max-width: 96vw` as a safety ceiling for the opposite case (a narrow-but-tall device where width becomes the binding constraint instead). Landscape places everything in a single `grid-row: 1`, so it needs its own `grid-template-rows: 1fr` override — without it, an empty unused row would silently inherit the portrait template's other `1fr` track and claim half of `.joysticks`' height for nothing.

**A flex `min-height: auto` trap surfaced by the fix above**: making `.joysticks` `height: 100%` should be enough on its own, but `.synth` (its parent, `flex: 1` inside `body`'s column flex layout) was still measured overflowing its own available space by ~40px on an 844px-tall viewport. A flex item's default `min-height` is `auto` (content-based), not `0` — and the percentage-height chain from `.joysticks` down through `.joystick` resolves as if `auto` while that content-based minimum is being computed (percentages are indeterminate during intrinsic sizing), producing an inflated natural size that becomes `.synth`'s floor and pushes it taller than `body` actually has. `.synth { min-height: 0; }` is the standard fix — let it actually shrink to its flex-resolved size instead of being floored by a circular content calculation.

**Center circles now show the live resolved chord name**: `#degree-center-label` and `#joy-center` sat empty in the markup — styled, never written to — until `updateChordNameLabel()` in `src/degree-joystick.js` started mirroring the same string into both on every `pressDegree()`/`releaseDegree()`/`setDirection()`. `resolvedChordName()` in `src/chords.js` builds it from the root note (`KEY_NAMES[(keyRoot + degree.semitone) % 12]`) plus a suffix looked up from an explicit `(quality, direction)` table (`CHORD_SUFFIXES`) rather than derived from `getChordIntervals()`'s raw numbers — a few combinations (minor+augmented, diminished+add9, ...) land on non-standard chords with no single obvious symbol to compute toward, so the table just states the answer for all 24. Monophonic-by-degree (see below) means at most one entry is ever held, so there's never an ambiguous "which chord" to pick between. Both centers deliberately show the *same* string rather than two different pieces of information — the modifier stick's wedges already fully describe what a direction does (`Dom7`, `Sus4`, ...), so there's nothing else useful to put there; mirroring it means the readout is visible near whichever stick your eyes/thumb are on mid-performance. Both sides render it case-sensitive (`Dsus2`) — the modifier stick's own static wedge labels stay uppercase (`.joy-label`, see Architecture above), but `.joy-center-label` was carved out as an explicit exception since an uppercased chord name (`DSUS2`) doesn't read correctly. Long names (root + a rarely-hit suffix like `sus2b5`, e.g. `C#sus2b5`) get a smaller inline `font-size` from `updateChordNameLabel()` itself (length-based: >7 chars → 9px, >5 → 10.5px) so they don't overflow the ~76px-diameter center circle.

**Fieldset border color**: `--wedge-stroke` looks like the obvious choice for a border color, but it's defined as `var(--bg)` itself (a deliberate choice for seamless wedge edges against the page background) — using it for `.controls`' border makes the border invisible, same color as what's behind it. `--panel-hover` is what's actually used instead, since it's a real step lighter than `--bg` in both themes.

**A fieldset sizing trap**: fieldsets have a legacy UA-stylesheet quirk that forces a minimum width based on content even when a grid/flex context asks them to shrink — but that quirk is specifically tied to a fieldset's *default* `display: block` rendering; switching `display` to `flex` (as `.controls` does) already sidesteps it in modern browsers, so no `min-width` override is needed. Adding one anyway (`min-width: 0`, reasoning "fieldsets are weird, better neutralize it") does something worse: it tells the CSS Grid track sizing algorithm this item is free to shrink *below* its buttons' natural content width, and it will — clipping the last button off the edge in portrait, confirmed via `getBoundingClientRect()`/`scrollWidth` showing the fieldset's rendered box narrower than its content.

**A cascade trap worth knowing about**: a rule with no media-query guard beats an earlier, more-specific-*looking* rule inside `@media (orientation: landscape)` for the same selector, purely by coming later in the source file — media queries add no specificity of their own. `.fx-toggles`/`.sound-controls`' base rule (row layout, used in portrait) sits *after* the landscape block that sets them to column layout, so without a second landscape override placed after the base rule too, the "always applies" row layout silently wins even in landscape. Restating the override after the culprit, not moving the culprit, is the fix — and it needs a comment, because the duplication looks like a mistake otherwise.

Voices are tracked per-degree by absolute pitch (`degreeKey:semitone`) and reconciled on every change (chord press, joystick move, key change) so only notes that actually enter/leave the chord get started/stopped — shared tones sustain without re-triggering their envelope.

**One degree sounds at a time.** `pressDegree()` releases whatever was held before starting the new one, so no input can stack two chords — the degree stick takes a single owning touch (`degreeTouchId`) and ignores further fingers until it lifts, and on the keyboard a second degree key steals from the first rather than adding to it. Note this makes the *degree* monophonic, not the synth: a degree is still a full chord of simultaneous voices, and the modifier stick is independently held on top of it. Lifting an ignored second finger deliberately doesn't end the owning touch.

**Glide** (off by default; toggle + a 20-400ms time slider, default 120ms, in the "Glide" dialog): when on, `audio.reconcileVoices()` — the same function that already diffs an old chord's voice ids against a new chord's and leaves ids common to both untouched — pairs off the *leftover* ids (present in only one side) nearest-pitch-to-nearest-pitch and slides each pair with `glideVoice()` (same oscillator/gain node throughout, no retriggered attack, just `osc.frequency.linearRampToValueAtTime()`) instead of hard `stopVoice()`/`startVoice()`-ing them. Any surplus when the chord grows or shrinks (a triad gaining a 7th, say) still hard starts/stops since it has no pairing partner — there's genuinely nothing to glide from/to, since the tone is being purely added or removed, not replaced (this is why e.g. `center → Dom7` never glides — it's a pure addition — while `Dom7 → 9th` does, since that swaps which extension tone is present). This reaches both a same-degree modifier change (`setDirection`, e.g. the Maj/Min toggle) and, since `pressDegree()`'s monophonic steal hands its outgoing voices to this same reconciliation instead of always releasing them outright, a degree-to-degree change too (I → V) — as long as the transition is *rolling*: a keyboard press while the previous key is still down, or a touch dragged from one wedge to another.

**Glide edges** (`audio.glideEdgesEnabled`, off by default, a second checkbox in the same "Glide" dialog, only meaningful while Glide itself is also on): extends gliding to that surplus. A purely-added tone starts at the nearest *surviving* chord tone's pitch and ramps to its own, via `startVoice()`'s optional third `glideFromFreq` argument, instead of attacking directly at pitch. A purely-removed tone ramps toward the nearest surviving tone while its gain fades, via `stopVoice()`'s optional second `glideToFreq` argument — the release is stretched to `max(RELEASE, GLIDE_TIME)` so the pitch actually arrives before the voice goes silent, rather than getting cut off mid-slide. "Nearest surviving tone" means nearest (by Hz) among the *final* chord's other frequencies, computed fresh per leftover id — not the departing/arriving chord as a whole, so each edge tone picks its own best neighbor independently.

This explicitly does *not* apply when `oldTarget` is empty — i.e. the very first chord pressed from silence, no degree held before. Every id in that press is "leftover fresh" with nothing else around it yet, so without this guard each note of a brand new chord would glide in from one of its own sibling notes (the only "nearest neighbor" candidates available), all three sliding into place from each other instead of attacking cleanly — audible as a phantom slur on the very first note of every phrase. `reconcileVoices()` checks `oldTarget.size === 0` and falls back to a hard start for the whole chord in that case, same as if edges glide were off.

Both joysticks' `touchmove` handlers specifically treat the narrow gap between adjacent wedges (widened since the corner-radius change — see below) as "no information" rather than "stop": `document.elementFromPoint()` there hits neither a wedge nor the center circle, so it's ignored and whatever was playing keeps playing, exactly like passing a finger between two adjacent piano keys' gap without lifting. Only a hit on the actual dead-center circle, or a point truly outside the joystick's bounds (`!el.closest('#degree-joystick'/'#joystick')`), is treated as a genuine release. Getting this distinction wrong (an earlier version released or fell back to 'center' the instant the gap was crossed) doesn't break non-glide play — an extra near-instant stop/start reads the same as before — but with glide on it broke every drag that happened to cross a gap into a spurious hop through the bare chord or center state before the real target, reading as "glide doesn't work" for the single most natural glide gesture (dragging across wedges).

**Hold** (off by default; a plain click-toggle, no dialog, since it has no adjustable parameter — `settings.holdEnabled` in `src/settings.js`): when on, both sticks latch on release instead of stopping. The *only* thing that resets a latched degree/modifier is releasing specifically while positioned over the dead-center circle — merely dragging through it, or lifting anywhere else (a wedge, the inter-wedge gap, or off the pad entirely), leaves it sounding. Selecting a new wedge always takes over immediately regardless of Hold, via the same monophonic-steal/`setJoyDirection` paths used everywhere else. Per input method:
- **Touch**: `touchmove` never resets while holding (dragging onto/through center is just ignored, same as the gap); only `touchend`/`touchcancel` checks whether the lift itself landed on the center circle.
- **Mouse**: has no discrete release event, so entering the center circle (`mouseenter`) is treated as the reset gesture unconditionally, hold or not — the existing per-wedge/whole-stick `mouseleave` resets are suppressed instead while holding.
- **Keyboard**: has no "drag to center" gesture at all, so `keyup` just latches — turning the Hold toggle *off* is the only way to release a keyboard-latched note, and it also force-releases anything latched via touch/mouse for consistency (`releaseAllHeld()` in `degree-joystick.js` plus `setJoyDirection('center')`).

Building this surfaced a real, previously-invisible bug in `modifier-joystick.js`'s `directionAtPoint()`: its center-circle check compared the hit element against an unscoped `document.querySelector('.joy-center')`, which — since both sticks' center circles share that class — always returned the *degree* stick's circle (first in document order), never the modifier stick's own. Touch-dragging onto the modifier stick's center had been silently falling through to "not center" all along; fixed by scoping the lookup to `modifierJoystick.joystickEl.querySelector('.joy-center')`.

**Envelope** (basic ADSR, linear ramps, always active — not an optional effect, so its "Env" button opens a `<dialog>` with no "Enabled" checkbox, the one exception to every other dialog's shape): `startVoice()` in `src/audio.js` schedules gain `0 → peak (0.15)` over `ENVELOPE_ATTACK` (default 10ms), then `peak → peak*ENVELOPE_SUSTAIN` over `ENVELOPE_DECAY` (default 100ms, landing at 70% of peak by default), then holds there with no further scheduled change until the voice stops. `stopVoice()` always releases from whatever the gain's *actual current value* is at that moment (`gainNode.gain.setValueAtTime(gainNode.gain.value, now)` before ramping to 0) — release firing mid-attack or mid-decay works correctly, not just release-from-sustain, since it captures the live value rather than assuming the envelope already finished. Sustain is a *fraction of peak* (0-100%), not an independent absolute volume, so it can never exceed the attack's own peak level. Changing any of the four sliders only affects voices started *after* the change — already-scheduled ramps on currently-sounding voices are left alone, same as `GLIDE_TIME` changes not retroactively altering an in-flight glide.

The modifier joystick is likewise single-owner. Each still tracks its touch by identifier, and both can be held at once (one finger per stick), so dragging between wedges without lifting works on either. `:hover` CSS is scoped to `@media (hover: hover)` since touch leaves a wedge "stuck" in `:hover` on most mobile browsers after a drag — touch relies solely on the JS-driven `.active` class.

**Stick dot**: a small circle on each joystick that follows the actual pointer/touch position (via `getScreenCTM()`, clamped to the wedge radius), giving the flat SVG pad a continuous analog-stick feel on top of the discrete wedge zones. Both joysticks get exactly one dot, shared between mouse and touch, and it stays visible at all times — resting at dead centre when nothing is driving it, which reads as the stick's neutral position. (The degree stick briefly had a dot per touch identifier plus a separate mouse-only dot; on a touch device the mouse one never received a `mousemove`, so it sat parked at centre looking like a second stuck touch point.)

**Effects**: a shared lowpass filter (BiquadFilterNode, default 2.5kHz cutoff/Q 1), tremolo (sine LFO amplitude-modulating a gain stage, default 5Hz/50% depth, off by default since it's a much more overt effect than the others), delay (DelayNode + feedback gain, defaults 280ms/32%/22% send), and algorithmic reverb (ConvolverNode with a synthesized impulse response — no external audio file, defaults 2.2s decay/18% send) are built lazily in `init()` (`src/effects.js`), one node/bus each shared by every voice. The "Filter"/"Tremolo"/"Delay"/"Reverb" buttons (in the center control column, alongside the key and waveform dropdowns) each open a `<dialog>` with a checkbox and a range slider per parameter — filter gets cutoff/resonance, tremolo gets rate/depth, delay gets time/feedback/send, reverb gets decay/send. Every slider updates live on `input` except reverb decay, which only commits on `change` since it regenerates the impulse response buffer. The filter's cutoff slider maps its 0-1 travel to frequency exponentially (`sliderToCutoff()` in `src/index.js`), not linearly, since pitch is perceived logarithmically. All four effects can be on, off, or any combination, independent of each other and of their own parameter values.

**Signal flow**: each voice's gain connects only to the shared filter (`effects.filterNode`), not straight to `destination`. The filter feeds the tremolo gain stage (`effects.tremoloGain`), which fans out to `destination` plus a parallel tap into each effect send — so filter then tremolo both land before the delay/reverb taps, and the echoes/tail come out filtered and pulsing too. The delay's output additionally feeds the reverb send as well as `destination` — so the echoes are reverberated rather than dry. That last edge matters more than it looks: without it the repeats are completely dry, which passes unnoticed at short delay times (they land while the original note's reverb tail is still ringing) but makes the space audibly drop out at long ones, since by then the tail is ~27dB down. Nothing downstream of the reverb returns to the delay, so there's no runaway path. `src/test-setup.js`'s mock node records its `connect()` calls so routing like this is assertable — state-only tests can't see a misrouted graph.

**Filter/tremolo on/off is a ramp, not a bypass**: delay and reverb are parallel sends with an always-live dry path underneath, so "off" just ramps their send gain to 0. The filter and tremolo are inserts — every voice routes through both — so neither has a separate dry path to fall back to; instead "off" ramps their parameters to values that pass audio through effectively unaffected (filter: `frequency`/`Q` to 20kHz/Q≈0; tremolo: LFO depth to 0 while its gain stage's baseline ramps to 1) over the same 50ms `FX_RAMP` window used elsewhere, leaving both nodes in the graph. Re-enabling ramps back to the configured values, not a fresh default. Tremolo's LFO (`effects.tremoloLFO`, a continuously-running `OscillatorNode`) feeds a depth-scaling gain node into the tremolo gain stage's own `gain` AudioParam — the classic tremolo circuit: the LFO swings ±depth/2 around a baseline of `1 - depth/2`, so output amplitude swings between `1 - depth` and `1` rather than modulating around silence.

## PWA

`manifest.webmanifest` (standalone display, icons, theme color) + `sw.js` (network-first cache of the app shell, falling back to cache only when actually offline) make the app installable and offline-capable, as an alternative/complement to the feature-detected Fullscreen button for chrome-free mobile launch. Icons live in `icons/` (`icon.svg` source + baked PNGs at 512/192/180 for manifest + `apple-touch-icon`).

**The service worker's `CACHE_NAME` is tied to the build-version tag** — bump both together on every deploy (see below), or `activate`'s old-cache cleanup never fires for that deploy.

**Why network-first, not stale-while-revalidate**: an earlier version served every GET from cache first (instantly, even the very next load after a deploy) and only refreshed the cache in the background for the load *after that*. That's fine for the page shell/icons but broke on days with several fast deploys (v33→v35 in one sitting): a visit could land mid-transition with a freshly-fetched `index.html` (new effect's dialog markup already present) paired with a still-cached `src/index.js` from before that effect's toggle button was wired up — the button renders but silently does nothing, since the JS actually running never learned it exists. Network-first fetches every resource fresh on every online load, so HTML and JS always come from the same deploy; the cache is now purely an offline fallback (`.catch()` on a failed `fetch()`), not a speed optimization.

## Conventions established in this project

- Every UI change gets verified in a live browser (chrome-devtools MCP tools) before considering it done — screenshot + console check minimum, often synthetic event dispatch to verify audio/state logic (oscillator start/stop counting for voice-lifecycle bugs).
- **Build version tag** (bottom-left corner, `v1`, `v2`, ...) — increment by 1 on every deploy so version is visible on-device, and keep `sw.js`'s `CACHE_NAME` in sync with it.
- **Debug panel** (bottom-right "debug" toggle) — on-page diagnostic log, added because the user can't plug their phone in for remote debugging. Kept intentionally for now; logs fullscreen API feature-detection, service worker registration, and click/promise tracing.
- Commit messages are detailed (what + why + how verified); push to `master` immediately deploys.
- Standing authorization to push directly to `master` without asking each time (see git log / CLAUDE.md).
- Fullscreen button only shown if `document.fullscreenEnabled` + `requestFullscreen` actually exist (confirmed absent on the user's Chrome mobile — don't re-add unconditionally).

## Known open items / suggested next steps

From the user's working todo list, still open as of this writing:

- **Light mode** — currently one (dark) theme only; no light-mode styles exist yet.
- **Left-hand keyboard support** — current keyboard bindings (`a s d f` / `w e r` / `1`-`7`) are one-handed on the right/number row; a left-hand-friendly binding scheme hasn't been designed.
- **More effects** — filter, tremolo, delay, and reverb are now built (see Architecture); open-ended: chorus/flanger (modulated delay), distortion (WaveShaperNode), stereo panning (StereoPannerNode), and compression (DynamicsCompressorNode) are all native-node options that haven't been built. A bitcrusher would need an AudioWorkletNode instead — no stock node does sample-rate reduction.
- Background/joystick-label polish items from the todo list ("fix background", "joy lables") were addressed this session (labels: uppercase + two-line split, see Architecture) — re-check `todo.md` directly if picking this up, since it's gitignored and may have moved on since this README was last updated.

Longer-standing items:

- Regression harness: a hidden test mode running oscillator start/stop assertions (triad→7th = +1 voice/0 stops, etc.) to catch future voice-lifecycle regressions without manual instrumentation.
- Envelope is currently linear-ramp ADSR only (see Architecture) — no curve shape (exponential/logarithmic) option, and no per-stage curve picker in the UI.
- `icons/icon.svg` circles sit close to the maskable safe-zone edge (~79% of the safe radius) — fine as "any" purpose icons, but don't add a "maskable" purpose entry without pulling them in first or Android's circular mask will clip the outer dots.
